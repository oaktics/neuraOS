# 復旧

## Runner停止・電源断

SQLite WALに記録したイベントとoutboxは再起動後も保持する。ACKを得ていないイベントを同じoperation IDで再配送する。古いfencing tokenのイベントは履歴としてのみ保存する。

実行権が切れたRunは30秒後の照合でblockedとなる。外部操作のdispatching状態はunknownへ変換する。UIで結果照合後に明示再開する。結果不明の送信は自動再送しない。

## 外部Issue作成直後に切断

GitHub側でIssue番号を調べ、Task Detail → 実行詳細に入力する。タイトル、本文、冪等マーカーを再取得して一致した場合のみ解決済みにする。見つからないことだけを未送信の証明にしない。

## バックアップ

ローカルの `pnpm backup export` はSQLiteスナップショットと成果物本文をJSONへ書き出し、独立した削除台帳も出力する。資格情報は含めない。OSディスク暗号化と保存先の暗号化は別途必要。

クラウドDBはNeonのPITRと別障害領域へのpg_dump、成果物はR2から別バケット・別プロバイダーへの複製を設定する。バックアップ保有だけで復元可能とは判定しない。

## 復元手順

1. Runnerを停止する。
2. 破損前のバックアップと、それ以降の削除も含む**最新の削除台帳**を取得する。台帳が不明なら復元して稼働させない。
3. 空のディレクトリを `NEURA_DATA_DIR` に指定する。
4. `NEURA_DELETION_LEDGER` を指定して `pnpm backup restore` を実行する。
5. ハッシュ・成果物数・完了基準・未解決外部操作を照合する。
6. 端末を再登録する。復元時に以前の端末は失効させる。
7. 新しいRunとして権限と作業範囲を確認する。

古いバックアップと古い削除台帳を同時に使えば、後日の削除を知ることはできない。削除台帳を独立して保護し、復旧時に最新性を確認する運用が必要。

RPO/RTO、p95同期・表示時間、実電源断・ログアウト・スリープの確認はリリース前の未完了項目。
